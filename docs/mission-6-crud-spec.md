# 미션 6 CRUD 기능 명세서

## 1. 문서 목적

테두리 랜딩 페이지의 견적 신청 흐름을 실제 Supabase 데이터와 연결하고, 신청 등록부터 조회·수정·삭제까지 하나의 사이클로 검증한다.

새로운 백엔드 서버는 만들지 않고 Next.js App Router와 Supabase를 사용한다. 기존 랜딩 페이지와 `/quote` UI는 유지하며, 이미 구현된 이메일 인증과 사진 업로드를 CRUD 흐름에 연결한다.

## 2. 핵심 기능 선정

### 기능명

견적 신청 관리

### 선정 이유

테두리의 핵심 가치는 방문자의 조경 요청을 접수하고 요청 내용을 바탕으로 견적 상담을 연결하는 것이다. 따라서 `quote_requests`를 핵심 CRUD 데이터로 선정한다.

### 대상 사용자와 인증

회원가입을 별도로 요구하지 않는 견적 신청자다. 사용자는 접수번호와 신청 이메일을 입력한 뒤 이메일 OTP 인증을 완료한다. Supabase Auth는 내부적으로 인증 세션을 만들지만, 사용자에게 별도 회원가입·비밀번호 설정을 요구하지 않는다.

접수번호만으로는 접근할 수 없게 한다. 접수번호는 추측될 수 있으므로 반드시 신청 이메일과 OTP를 함께 확인한다.

## 3. 사용자 흐름

```text
/quote → 이메일 인증 → 견적 신청 등록(Create)
       → 접수번호·이메일 입력 → 이메일 OTP 인증
       → /my 목록(Read) → /my/[id] 상세(Read)
       → /my/[id]/edit 수정(Update) → 삭제 확인(Delete)
```

### 등록

- `/quote`에서 지역, 주택 유형, 작업 범위, 희망 시기, 연락처 등을 입력한다.
- 이메일 OTP 인증을 완료해야 제출할 수 있다.
- 사진은 최대 5장, JPG·PNG·WebP, 파일당 최대 10MB다.
- 제출 중 버튼을 비활성화해 중복 등록을 막는다.
- 성공하면 접수번호를 보여주고 `/my` 또는 상세 화면으로 이동할 수 있다.
- 실패 시 필수값, 사진 업로드, Supabase 오류를 구분해 안내한다.

### 목록

- `/my`에서 접수번호와 신청 이메일로 본인 확인을 시작한다.
- 이메일 OTP 인증이 완료되면 인증된 이메일의 신청만 최신순으로 조회한다.
- 한 페이지에 10건을 표시하고 이전·다음 페이지를 제공한다.
- 신청이 없으면 빈 상태와 새 견적 신청 CTA를 표시한다.
- 접수번호, 지역, 작업 범위, 상태, 신청일을 표시한다.

접수번호를 모르는 경우에는 신청 이메일로 받은 접수 메일을 확인하도록 안내한다. 접수번호만 입력했거나 이메일 인증에 실패하면 신청 내용을 표시하지 않는다.

### 상세

- `/my/[id]`에서 신청 전체 내용과 사진을 확인한다.
- 접수번호, 상태, 신청 정보, 작업 범위, 일정, 예산, 연락처를 표시한다.
- 사진이 없으면 사진 없음 상태를 표시한다.
- 존재하지 않거나 권한 없는 ID는 정보가 노출되지 않는 안내 화면으로 처리한다.
- 수정·삭제 버튼을 제공한다.

### 수정

- `/my/[id]/edit`에서 기존 값을 불러와 수정한다.
- 지역, 주택 유형, 작업 범위, 범위, 사진, 희망 사항, 일정, 예산, 방문 방식, 이름, 전화번호를 수정한다.
- 접수번호, 사용자 ID, 상태, 생성일은 수정할 수 없다.
- 저장 중 중복 제출을 막고, 성공하면 상세 화면으로 돌아간다.
- 취소하면 변경사항을 저장하지 않고 상세 화면으로 돌아간다.

### 삭제

- 삭제 버튼을 누르면 확인 절차를 거친다.
- 신청 내용과 연결 사진을 복구할 수 없음을 안내한다.
- 레코드와 연결된 Storage 사진을 함께 정리한다.
- 성공하면 `/my` 목록으로 이동하고, 실패하면 데이터를 남긴 채 오류를 표시한다.

### 진행 상태

- `received`, `checking`, `needs`, `quoted`, `done`, `canceled` 상태를 표시한다.
- 진행 상태는 운영자 또는 견적 처리 시스템만 변경한다.
- 신청자는 상태를 조회할 수 있지만 직접 변경할 수 없다.

## 4. 데이터 구조

### `public.quote_requests`

| 컬럼 | 타입 | 필수 | 규칙 |
|---|---|---:|---|
| `id` | uuid | 예 | 기본키, 자동 생성 |
| `receipt_no` | text | 자동 | `TD-YYMM-0001`, unique |
| `user_id` | uuid | 예 | `auth.users.id`와 연결 |
| `email` | text | 예 | 인증된 이메일과 일치 |
| `region` | text | 예 | 서울·경기·인천 |
| `district` | text | 예 | 선택 지역 |
| `housing` | text | 예 | 주택 유형 |
| `works` | text[] | 예 | 선택 작업 목록 |
| `works_unknown` | boolean | 예 | 작업 미정 여부 |
| `scope` | text | 예 | 자재·배송·시공 범위 |
| `photo_paths` | text[] | 예 | Storage 경로, 최대 5개 |
| `size_note` | text | 아니오 | 규모 메모 |
| `wish` | text | 아니오 | 요청사항과 방문 방식 |
| `timing` | text | 예 | 희망 시기 |
| `budget` | text | 아니오 | 예산 |
| `name` | text | 아니오 | 신청자 이름 |
| `phone` | text | 아니오 | 연락처 |
| `privacy_agreed_at` | timestamptz | 예 | 개인정보 동의 시각 |
| `terms_agreed_at` | timestamptz | 예 | 약관 동의 시각 |
| `status` | text | 예 | `received` 등 진행 상태 |
| `created_at` | timestamptz | 예 | 등록 시각 |
| `updated_at` | timestamptz | 추가 예정 | 수정 시각 |

### Storage: `quote-photos`

- 비공개 버킷
- 허용 형식: `image/jpeg`, `image/png`, `image/webp`
- 최대 파일 크기: 10MB
- 경로: `{user_id}/{uuid}.jpg`
- 레코드의 `photo_paths`에 Storage 경로를 저장한다.

## 5. 비회원 접근 및 보안 규칙

- 사용자에게 회원가입을 요구하지 않는다.
- 접수번호만으로는 조회·수정·삭제할 수 없다.
- 접수번호와 신청 이메일이 일치하고 이메일 OTP 인증이 완료된 경우에만 접근한다.
- 인증된 사용자는 자신의 이메일에 연결된 신청만 조회·수정·삭제할 수 있다.
- URL에 다른 신청의 ID를 입력해도 데이터가 노출되지 않는다.
- `user_id`, `receipt_no`, `status`, `created_at`은 일반 사용자 수정 대상에서 제외한다.
- 실제 환경변수 값과 비밀 키는 저장소와 문서에 기록하지 않는다.

## 6. 화면 및 라우팅

| 경로 | 역할 |
|---|---|
| `/quote` | 견적 신청 등록 |
| `/my` | 접수번호·이메일 확인 및 내 신청 목록 |
| `/my/[id]` | 신청 상세 |
| `/my/[id]/edit` | 신청 수정 |
| `/api/quote-notify` | 등록 후 알림 메일 전송 |

기존 버튼·상태 배지·카드 컴포넌트는 재사용한다.

## 7. 상태 처리

- 목록·상세 조회 중: 로딩 UI 표시
- 저장·삭제 중: 버튼 비활성화와 처리 중 문구 표시
- 신청이 없거나 사진이 없을 때: 각각 빈 상태 표시
- 필수값·이메일·전화번호·파일 형식·용량 오류: 입력 가까이에 안내
- 존재하지 않는 상세 주소: `notFound()` 또는 전용 안내 화면
- 권한 오류: 존재하지 않는 신청처럼 처리해 정보 노출 방지
- Supabase 오류: 재시도 가능한 일반 오류 메시지 표시

## 8. QA 체크리스트

- [ ] 빈 필수값 제출이 차단된다.
- [ ] 잘못된 이메일·전화번호가 차단된다.
- [ ] 사진 형식·크기·개수 제한이 동작한다.
- [ ] 정상 등록 후 접수번호가 표시된다.
- [ ] 등록 데이터가 목록과 상세에 표시된다.
- [ ] 새로고침 후에도 데이터가 유지된다.
- [ ] 수정 후 목록과 상세에 변경 내용이 반영된다.
- [ ] 삭제 확인 없이 삭제되지 않는다.
- [ ] 삭제 후 목록에서 사라지고 Storage 사진도 정리된다.
- [ ] 존재하지 않는 상세 주소가 적절히 처리된다.
- [ ] 다른 사용자의 신청 ID에 접근할 수 없다.
- [ ] 접수번호만으로 신청 내용이 노출되지 않는다.
- [ ] 접수번호와 이메일이 일치하지 않으면 인증 코드가 발송되지 않거나 접근이 차단된다.
- [ ] 회원가입 없이 이메일 OTP만으로 신청을 조회할 수 있다.
- [ ] 진행 상태는 신청자가 변경할 수 없다.
- [ ] 빈 목록·조회 오류·저장 오류·업로드 오류가 각각 표시된다.
- [ ] Vercel 배포 환경에서 등록·조회·수정·삭제·사진 업로드를 확인한다.

## 9. 구현 순서

1. `updated_at`과 수정·삭제 RLS 정책을 Supabase 마이그레이션에 추가한다.
2. 견적 타입과 Supabase 조회 함수를 정리한다.
3. `/my` 목록과 페이지네이션을 구현한다.
4. `/my/[id]` 상세 화면을 구현한다.
5. `/my/[id]/edit` 수정 화면과 사진 교체를 구현한다.
6. 삭제 확인과 Storage 파일 정리를 구현한다.
7. 로딩·빈 상태·오류 상태를 보완한다.
8. README, `CODEX_HANDOFF.md`, QA 결과를 갱신한다.
9. 로컬과 Vercel에서 전체 CRUD를 점검한다.

## 10. 완료 기준

등록 → 목록 → 상세 → 수정 → 삭제 흐름이 실제 Supabase 데이터로 동작하고, 새로고침·권한·오류·파일 업로드 시나리오가 QA 체크리스트를 통과하면 미션 6 기본 요구사항을 완료한 것으로 본다.
